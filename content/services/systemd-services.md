## story | The app that died when Samir went home

Lumen's first internal tool, a small notes API, ran on a server because Samir had started it by hand: `node server.js &` in his SSH session. It worked for weeks. Then the server rebooted for security patches on a Sunday, and on Monday the tool was gone. The week after, it crashed at 2 a.m. on a bad request and stayed down until someone noticed at 9.

Nothing was wrong with the code. What was missing was a **supervisor**: something that starts the app at boot, restarts it when it crashes, runs it as a dedicated user, and keeps its logs in one place. On Linux, that is **systemd**.

## model | Units, states and the journal

**systemd** is PID 1: the first process, parent of everything else. It manages **units**; a **service unit** describes one long-running program:

```diagram
systemd
```

A minimal unit file, `/etc/systemd/system/notes.service`:

```term
[Unit]
Description=Lumen notes API
After=network.target

[Service]
User=notes
WorkingDirectory=/opt/notes
Environment=PORT=4000
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

| Line | Means |
|---|---|
| `After=network.target` | start once networking is up |
| `User=` | run as this user, not root |
| `Environment=` / `EnvironmentFile=` | configuration for the app |
| `ExecStart=` | the command, with an absolute path |
| `Restart=always` / `on-failure` | what to do when it exits |
| `WantedBy=multi-user.target` | what `enable` hooks it into at boot |

Two separate ideas trip people up:

- **start/stop** changes what runs *now*.
- **enable/disable** changes what starts *at boot*. `enable --now` does both.

After editing a unit file, run `systemctl daemon-reload`, or systemd keeps using the old version.

Everything a service prints to stdout and stderr goes to the **journal**, read with `journalctl`.

## commands | Running services

```term
$ sudo systemctl daemon-reload            # after creating or editing a unit
$ sudo systemctl enable --now notes       # start now and at every boot
$ systemctl status notes                  # state, PID, memory, last log lines
$ sudo systemctl restart notes            # stop + start
$ sudo systemctl reload nginx             # re-read config without stopping (if supported)
$ systemctl is-active notes               # scriptable: prints active/inactive/failed
$ systemctl --failed                      # everything broken
$ journalctl -u notes -n 50               # last 50 log lines of one service
$ journalctl -u notes -f                  # follow
$ journalctl -u notes --since "10 min ago"
$ systemctl cat notes                     # the unit file systemd is using
```

## analogy | A stage manager

A theatre's stage manager does not act. They know every performer's cue, call them on stage at the right moment, send in the understudy when someone collapses, and keep the show log. Your app is a performer; systemd is the stage manager; the unit file is the cue sheet; the journal is the show log.

## team | Services in a real team

- **Every long-running process is a unit.** No `nohup`, no `screen` sessions, no "started by hand".
- **One user per service**, with `/usr/sbin/nologin` as its shell, owning only its own files.
- **Restart policies with limits**: `Restart=on-failure` plus systemd's start limit stops a crash loop from hammering a database.
- **Unit files in version control** (or generated by configuration management), never edited live without a record.

## traps | systemd traps

**Forgetting `daemon-reload`.** You edit the file, restart, and nothing changes; `systemctl status` warns that the unit changed on disk.

**Relative paths in `ExecStart`.** systemd does not use your shell's PATH or cwd; use absolute paths and `WorkingDirectory=`.

**Running as root by default.** Without `User=`, the service runs as root.

**`enable` without `start`** (or the reverse): it works now but not after a reboot, or after a reboot but not now.
